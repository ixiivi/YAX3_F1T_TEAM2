# 개인 작업 기록: 제어판과 자율주행 코드

**개인 작업 기록이고 팀 표준이 아니다.** 팀 작업은 `f1tenth_team_ws`에서 시작한다. 이 브랜치는 `main`에 합치지 않는다. 막혔을 때 참고하거나 백업으로 쓴다. 대회 수준으로 검증된 코드가 아니다.

## 구성

| 파일 | 역할 |
|---|---|
| `control_panel.py`, `panel.sh` | PyQt5 제어판. 아래 노드를 자식 프로세스로 띄운다 |
| `keyboard_teleop.py` | 터미널 키보드 조종. 속도 단계와 램프는 제어판도 함께 쓴다 |
| `save_map.sh` | SLAM 맵 저장 |
| `f1tenth.rviz` | RViz 설정 |
| `src/waypoint_nav/` | ROS 패키지: `waypoint_editor`, `rviz_waypoints`, `pure_pursuit`, `global_localize`, `scan_match`, AMCL 설정 |
| `patches/` | 차량 패치. `f1tenth_team_ws`에 적용된 것과 같은 내용 |
| `MAC_GUI_HANDOFF.md` | 맥북용 원격 제어판 설계. 구현하지 않음 |

맵은 용량 문제(86 MB)로 넣지 않았다.

## 실행

코드의 경로가 `~/f1tenth_ws`로 고정돼 있다.

1. `f1tenth_system`을 `~/f1tenth_ws/src`에 두고 `patches/`를 적용한다.
2. `src/waypoint_nav`를 `~/f1tenth_ws/src`로, 나머지 파일을 `~/f1tenth_ws`로 복사한다.
3. `~/f1tenth_ws`에서 `colcon build`를 실행한다.
4. `~/f1tenth_ws/panel.sh`로 제어판을 켠다.

`f1tenth_team_ws`와 동시에 드라이버를 띄울 수 없다. VESC와 라이다를 함께 쓰기 때문이다.

## 돌아가는 흐름

```
드라이버(bringup) → SLAM으로 맵 제작 → 맵 저장 → 웨이포인트 편집
                                                    ↓
              자율주행 ← 출발 ← 자율주행 준비 ← 위치 추정(AMCL)
```

| 제어판 항목 | 실행하는 것 |
|---|---|
| 드라이버 | `ros2 launch f1tenth_stack bringup_launch.py` |
| SLAM | `slam_toolbox online_async_launch.py` (위치 추정과 동시 사용 불가) |
| 맵 저장 | `save_map.sh <이름>` (SLAM이 켜져 있을 때만) |
| 웨이포인트 편집 | `waypoint_editor <map.yaml>`: 클릭으로 점을 찍으면 경로를 다듬고 속도를 계산해 CSV로 저장 |
| 위치 추정 | `localize_launch.py map:=<map.yaml>`: map_server, AMCL, 시작 위치를 찾는 `global_localize` |
| 위치 다시 찾기 | `global_localize`: 스캔 하나를 맵 전체와 비교 |
| 자율주행 준비 | `pure_pursuit` 실행. 정지 상태로 대기 |
| 출발 / 정지 | `/pure_pursuit/command`에 `go` / `stop` 발행 |
| 키보드 조종 | `/teleop`에 20 Hz 발행 (WASD, X 조향 중앙, Space 감속 정지, B 즉시 정지) |
| 긴급 정지 | `/pure_pursuit/command`에 `estop`, 이후 `/teleop`에 0,0을 계속 발행 |

`/teleop`(우선순위 100)이 자율주행의 `/drive`(10)보다 우선한다. **긴급 정지는 제어판이 살아서 발행하는 동안만 유지된다.** 제어판이 죽으면 `/teleop`이 끊기고 mux는 `/drive`로 돌아간다.

## pure_pursuit가 하는 일

- **경로 추종:** 전방 주시 거리 = 0.6 + 0.4 × 속도 [m]. 최저 속도 0.5 m/s에 조향량만큼 더한다.
- **AEB:** 앞으로 달릴 호 위에 스캔 점이 있으면 정지한다.
- **장애물 우회:** 맵 벽에서 0.25 m 넘게 떨어진 스캔 점을 장애물로 보고 경로를 옆으로 민다(최대 0.6 m).
- **주행 중 위치 보정:** 스캔이 맵 벽과 맞는 비율(fit)이 70% 아래면 주변(0.5 m, ±15°)을 탐색하고, 75% 이상 맞는 자세를 찾으면 멈추지 않고 AMCL에 넘긴다.
- **위치 복구:** fit이 45% 아래로 1초 이어지면 정지 → 지나온 길로 후진 → 재탐색. 3번 실패하면 멈춘다.
- **맵 확인:** 웨이포인트의 10% 이상이 맵 밖이면 시작을 거부한다.

## 겪은 문제

| 문제 | 원인 | 대응 |
|---|---|---|
| 정지할 때 바퀴가 뒤로 튐 | 0 ERPM 근처의 센서리스 속도 제어 | 0.3 m/s 미만은 브레이크 전류 |
| odom 방향이 반대 | FW 7의 ERPM 부호 | `vesc_to_odom` 부호 수정 |
| AMCL 시작 전 odom TF 없음 | 첫 서보 명령 전 odom 미발행 | 명령 전에도 발행 |
| "맵과 23%만 맞음" | AMCL과 다른 맵의 웨이포인트 선택 | 제어판과 `pure_pursuit`에서 차단 |
| 출발 직후 fit 19~39%로 반복 정지 | 주행 중 위치가 틀어짐 | 주행 중 보정 추가. **근본 해결 아님, 아래 참고** |

## 해결되지 않은 문제: 주행 중 위치 틀어짐

정지 상태에서는 fit이 98~99%인데 움직이면 떨어진다. 주행 중 보정을 넣은 뒤의 로그(주행 3회, DLAB 맵, 2026-11-03)는 다음과 같다.

| 항목 | 값 |
|---|---|
| 보정 횟수 | 133번 (한 번의 주행에서만 121번) |
| 위치 보정량 | 중앙값 9 cm, 최대 29 cm |
| 각도 보정량 | 중앙값 7.7°, 최대 20.1° |
| 전체 복구 사례 | 추정 위치와 170 cm, -34.9° 차이 |

보정은 동작하지만 계속 다시 틀어지므로 증상을 덮는 수준이다. 위치보다 각도 오차가 두드러진다. **조향 게인이나 속도 게인이 맞지 않아 odom이 틀어지는 것으로 추정하지만, 아직 검증하지 않았다.** 스캔 타임스탬프 지연도 확인이 필요하다. 한 바퀴를 안정적으로 완주하는지는 이 로그만으로 알 수 없다.

## 아직 안 한 것

- `speed_to_erpm_gain`(4614), `steering_angle_to_servo_gain`(-1.2135) 캘리브레이션. 이전 팀의 차는 4203, 1.6배 과조향이었다.
- odom을 보강할 IMU. 이전 팀 코드는 자이로 odom을 썼다.
- 고속 주행 시험. 시험 속도는 약 1 m/s다.
- 제어판이 죽었을 때의 안전 정지. 조이패드 데드맨 등 별도 수단이 필요하다.
